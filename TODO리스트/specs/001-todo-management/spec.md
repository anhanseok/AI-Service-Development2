# Feature Specification: 할 일 관리 (Todo Management)

**Feature Branch**: `001-todo-management`

**Created**: 2026-09-16

**Status**: Draft

**Input**: User description: "사용자가 할 일을 추가하고, 목록을 확인하고, 완료 여부를 토글하고, 삭제할 수 있는 기능이 필요하다. 할 일에는 제목(필수)과 완료 여부가 있다."

## Clarifications

### Session 2026-09-16

- Q: 이미 있는 할 일과 똑같은 제목을 또 추가할 수 있어야 하나요? → A: 중복 허용. 같은 제목을 몇 개든 따로 만들 수 있다.
- Q: 할 일 제목은 최대 몇 글자까지 입력할 수 있어야 하나요? → A: 100자.
- Q: 할 일을 삭제할 때 확인을 받아야 하나요? → A: 확인을 받는다. 취소하면 삭제되지 않는다.
- Q: 완료 표시한 할 일은 목록에서 어떻게 보여야 하나요? → A: 미완료 목록과 완료 목록을 위아래로 분리해서 보여준다.
- Q: 여러 탭에서 동시에 열었을 때 한쪽의 변경이 다른 쪽에 어떻게 반영되나요? → A: 5초 이내 자동 반영. 그래도 실패하는 동작은 안내 후 목록 재동기화.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 할 일 기록하고 확인하기 (Priority: P1)

사용자는 머릿속에 있는 해야 할 일을 잊지 않기 위해 제목을 적어 목록에 남긴다. 화면을 열면
지금까지 적어둔 할 일이 한눈에 보인다.

**Why this priority**: 적고 다시 볼 수 없으면 이 기능은 존재 이유가 없다. 이 스토리 하나만
구현해도 "메모로 쓰는 할 일 목록"으로서 실제 가치를 준다.

**Independent Test**: 할 일 제목을 입력해 추가한 뒤 목록에 나타나는지, 화면을 새로 열었을 때도
그대로 남아 있는지 확인하면 단독으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 할 일이 하나도 없는 상태에서, **When** 사용자가 제목을 입력하고 추가하면,
   **Then** 그 할 일이 미완료 구역 맨 위에 나타난다.
2. **Given** 할 일이 여러 개 저장된 상태에서, **When** 사용자가 화면을 새로 열면,
   **Then** 저장된 할 일이 모두 그대로 보인다.
3. **Given** 제목 입력란이 비어 있거나 공백만 있는 상태에서, **When** 사용자가 추가를 시도하면,
   **Then** 할 일이 추가되지 않고 제목이 필요하다는 안내가 표시된다.

---

### User Story 2 - 완료 여부 표시하기 (Priority: P2)

사용자는 끝낸 일과 남은 일을 구분하기 위해 각 할 일의 완료 표시를 켜고 끈다.

**Why this priority**: 진행 상황을 알 수 없으면 목록이 계속 쌓이기만 한다. 다만 기록 자체가
먼저 가능해야 의미가 있으므로 P1 다음이다.

**Independent Test**: 목록에 있는 할 일의 완료 표시를 켰다 끄고, 화면을 새로 열어도 그 상태가
유지되는지 확인하면 단독으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 미완료 상태의 할 일이 있을 때, **When** 사용자가 완료 표시를 켜면,
   **Then** 그 할 일은 완료 상태로 바뀌어 미완료 구역에서 사라지고 완료 구역에 나타난다.
2. **Given** 완료 상태의 할 일이 있을 때, **When** 사용자가 완료 표시를 끄면,
   **Then** 그 할 일은 다시 미완료 상태가 되어 미완료 구역으로 돌아간다.
3. **Given** 완료 상태를 바꾼 뒤, **When** 사용자가 화면을 새로 열면,
   **Then** 바뀐 완료 상태가 그대로 유지된다.

---

### User Story 3 - 필요 없어진 할 일 지우기 (Priority: P3)

사용자는 더 이상 관리할 필요가 없는 할 일을 목록에서 영구히 없앤다.

**Why this priority**: 없어도 기록과 완료 관리는 동작한다. 목록이 길어졌을 때의 정리 수단이므로
가장 마지막이다.

**Independent Test**: 특정 할 일을 삭제한 뒤 목록에서 사라지고, 화면을 새로 열어도 돌아오지
않는지 확인하면 단독으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 할 일이 목록에 있을 때, **When** 사용자가 삭제를 실행하고 확인하면,
   **Then** 그 할 일은 목록에서 사라지고 다른 할 일은 영향을 받지 않는다.
2. **Given** 삭제 확인 요청이 표시된 상태에서, **When** 사용자가 취소하면,
   **Then** 할 일은 삭제되지 않고 그대로 남는다.
3. **Given** 할 일을 삭제한 뒤, **When** 사용자가 화면을 새로 열면,
   **Then** 삭제된 할 일은 나타나지 않는다.

---

### Edge Cases

- 제목에 공백만 입력하거나 아무것도 입력하지 않고 추가를 시도하면 어떻게 되는가?
  → 추가를 거부하고 사유를 안내한다.
- 제목 앞뒤에 공백이 붙어 있으면 어떻게 저장되는가?
  → 앞뒤 공백을 제거한 값으로 저장한다.
- 제목이 100자를 넘으면 어떻게 되는가?
  → 추가를 거부하고 최대 100자임을 안내한다.
- 할 일이 하나도 없을 때 화면은 무엇을 보여주는가?
  → 두 구역 모두 비어 있음을 알리는 안내를 표시한다.
- 한쪽 구역만 비어 있으면(예: 완료한 일이 아직 없을 때) 화면은 무엇을 보여주는가?
  → 그 구역에 항목이 없음을 알리는 안내를 표시하고, 다른 구역은 정상적으로 보여준다.
- 이미 삭제된 할 일에 대해 완료 토글이나 삭제를 다시 시도하면 어떻게 되는가?
  → 동작을 수행하지 않고 대상이 없음을 안내한 뒤, 목록을 최신 상태로 다시 불러온다.
- 같은 화면을 두 곳에 열어두고 한쪽에서 할 일을 바꾸면 다른 쪽은 어떻게 되는가?
  → 별도 조작 없이 5초 이내에 바뀐 내용이 반영된다.
- 추가·토글·삭제가 실패하면 사용자는 그 사실을 알 수 있는가?
  → 실패 사유를 담은 안내를 표시하고, 화면의 목록은 실제 저장 상태와 일치시킨다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 사용자가 제목을 입력해 새 할 일을 추가할 수 있도록 MUST 제공한다.
- **FR-002**: 시스템은 제목이 비어 있거나 공백만으로 이루어진 경우 추가를 MUST 거부하고,
  제목이 필요하다는 안내를 표시한다.
- **FR-003**: 시스템은 제목의 앞뒤 공백을 제거한 뒤 MUST 저장한다.
- **FR-004**: 시스템은 제목이 100자를 초과하면 추가를 MUST 거부하고, 최대 100자임을 안내한다.
- **FR-005**: 새로 추가된 할 일은 MUST 미완료 상태로 시작한다.
- **FR-006**: 시스템은 저장된 할 일을 미완료 구역과 완료 구역으로 나누어 MUST 표시한다.
  미완료 구역이 완료 구역보다 위에 온다.
- **FR-007**: 시스템은 각 구역 안에서 최근에 추가된 할 일이 먼저 오도록 MUST 정렬한다.
- **FR-008**: 사용자는 개별 할 일의 완료 여부를 미완료↔완료로 MUST 전환할 수 있다. 전환된
  할 일은 반대편 구역으로 MUST 이동한다.
- **FR-009**: 사용자는 개별 할 일을 목록에서 MUST 삭제할 수 있다.
- **FR-010**: 시스템은 삭제를 실행하기 전에 사용자에게 MUST 확인을 받는다. 확인을 취소하면
  할 일은 삭제되지 않는다.
- **FR-011**: 추가·완료 전환·삭제의 결과는 화면을 다시 열어도 MUST 유지된다.
- **FR-012**: 시스템은 할 일이 하나도 없을 때, 그리고 어느 한 구역에 해당하는 할 일이 없을 때
  각각 비어 있음을 알리는 안내를 MUST 표시한다.
- **FR-013**: 추가·완료 전환·삭제가 실패한 경우 시스템은 사용자에게 실패 사실을 MUST 알리고,
  화면에 보이는 목록을 실제 저장 상태와 MUST 일치시킨다.
- **FR-014**: 시스템은 존재하지 않는 할 일에 대한 완료 전환·삭제 요청을 MUST 거부하고,
  대상이 없음을 안내한다.
- **FR-015**: 시스템은 기존 할 일과 제목이 완전히 같더라도 새 할 일 추가를 MUST 허용한다.
  제목 중복은 오류로 취급하지 않는다.
- **FR-016**: 화면이 열려 있는 동안 시스템은 목록을 주기적으로 MUST 갱신한다. 다른 창이나
  탭에서 생긴 추가·완료 전환·삭제가 5초 이내에 화면에 반영되어야 한다.

### Key Entities *(include if feature involves data)*

- **할 일 (Todo)**: 사용자가 관리하려는 하나의 작업 항목.
  - 제목 — 필수. 공백만으로는 구성될 수 없으며 앞뒤 공백은 제거된다. 다른 할 일과 제목이
    같아도 무방하다(중복 허용).
  - 완료 여부 — 완료 또는 미완료 두 가지 상태만 가진다. 생성 시 미완료. 이 값이 할 일이
    어느 구역에 표시될지를 결정한다.
  - 생성 시점 — 목록 정렬 순서를 정하는 데 쓰인다.
  - 각 할 일은 서로 독립적이며, 다른 할 일이나 사용자 계정과의 관계를 갖지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 화면을 연 뒤 10초 이내에 새 할 일 하나를 추가할 수 있다.
- **SC-002**: 추가·완료 전환·삭제를 실행하면 그 결과가 1초 이내에 화면에 반영된다.
- **SC-003**: 화면을 닫았다가 다시 열었을 때 이전에 저장한 할 일이 100% 그대로 남아 있다.
- **SC-004**: 이 화면을 처음 쓰는 사용자가 별도 설명 없이 추가·조회·완료 전환·삭제
  네 가지 동작을 모두 첫 시도에 성공한다.
- **SC-005**: 할 일이 100개 있을 때도 목록 전체가 2초 이내에 표시된다.
- **SC-006**: 같은 화면을 두 곳에 열어둔 상태에서 한쪽에서 할 일을 추가·완료 전환·삭제하면,
  다른 쪽에서 아무 조작을 하지 않아도 5초 이내에 같은 내용이 보인다.

## Assumptions

- 단일 사용자가 자신의 할 일만 관리한다. 로그인, 계정, 사용자 간 공유는 범위 밖이다.
- 제목의 최대 길이는 100자다(2026-09-16 명확화로 확정). 한 줄 제목에는 충분하며 그 이상은
  제목이 아니라 설명에 가깝다고 판단했다.
- 목록 정렬은 최근에 추가한 순서로 둔다. 원문에 명시가 없어 방금 적은 항목을 먼저 보는 것이
  자연스럽다고 판단했다.
- 삭제는 되돌릴 수 없으며, 실수를 막기 위해 실행 전 확인을 받는다. 휴지통이나 실행 취소는
  범위 밖이다.
- 마감일, 중요도, 카테고리, 검색, 정렬 변경, 완료 항목 일괄 삭제는 이번 범위에 포함하지 않는다.
- 같은 사용자가 여러 탭이나 창에서 동시에 열어 쓸 수 있다고 가정한다. 목록을 어떤 방식으로
  갱신할지(주기적 재조회, 서버 푸시 등)는 이 문서의 범위가 아니며 설계 단계에서 정한다.
- 사용자는 최신 브라우저가 설치된 데스크톱 환경에서 사용한다. 전용 모바일 화면 최적화는
  범위 밖이다.
