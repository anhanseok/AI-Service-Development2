## Question

체크리스트:

- API 응답을 curl/Postman 등으로 직접 확인
- 발견된 버그 수정

## Answer

프로덕션 빌드(`npm run build`) 성공 확인 후, **UTC 시간대로 실행한 프로덕션 서버**에 대해 전체 플로우 13항목 자동 검증 — 전부 통과.
(로그인 페이지 / 라우트 보호 / 캘린더 생성 / 일정 생성·조회·수정·삭제 / 초대 / 상대 목록 노출 / 상대의 조회·추가 / 양방향 확인)

### 발견하고 고친 버그: 월 경계 일정이 옆 달로 새는 문제

`GET /api/calendars/:id/events`가 `year`, `month`를 받아 서버에서 `new Date(year, month-1, 1)`로 범위를 만들고 있었다. 이 계산은 **서버 시간대** 기준이라, 서버(Vercel = UTC)와 사용자(KST, +9)가 다르면 경계가 어긋난다.

재현: 한국 사용자가 만든 "10월 1일 00:30" 일정(= UTC 9월 30일 15:30)을
- KST 서버(로컬 개발): 10월 조회에 정상 노출 → **버그가 안 보임**
- UTC 서버(배포 환경): 10월 조회 0개, 9월 조회에 잘못 노출 → **일정이 사라진 것처럼 보임**

수정: 시간대를 아는 쪽은 브라우저뿐이므로, 클라이언트가 월의 시작/끝을 자기 시간대로 계산해 절대 시각(ISO)으로 `from`/`to`에 보내고 API는 그대로 사용. 서버 시간대 의존성이 사라짐. 수정 후 KST/UTC 양쪽 서버에서 동일하게 동작 확인.

이 버그는 로컬에서만 테스트했다면 배포 직후에야 드러났을 문제다 — 09번 배포 전에 UTC로 돌려본 것이 실제로 값을 했다.

### 남은 확인 사항
- 맵의 "아직 안 정해진 것"에 있던 *타임존이 다른 멤버 간 표시 차이*: 일정은 절대 시각(UTC)으로 저장되고 각자 로컬 시간으로 표시되므로, 해외 멤버에게는 다른 시각으로 보인다. MVP 사용자(같은 시간대)에겐 문제없어 그대로 두고, 필요해지면 별도 티켓으로 다룰 것.
